    Delegation:
    - Implementation may go to codex (max effort) against pre-written contracts and failing tests; the quantizer's tests and the T12 latency-guarantee amendment are architecture work and stay with Fable. Codex must not modify tests.
    Architecture (decided):
    - The scheduler (ui/shared/auto-preview-scheduler.ts) stays untouched: it still decides WHEN a strike is due. Add a pure strike-time quantizer between the scheduler's retrigger command and the note layer's strike: (loop phase, cycle period T, strike kind, now, wait budget) → strike time. The engine/note layer defers the strike with one cancellable timer; cancellation/suspension rules unchanged.
    - Phase sources, in preference order: (a) if the MSEG is note-retriggered, no telemetry is needed — phase is time since OUR last strike modulo T, so sync is pure arithmetic keeping strikes an integer number of cycles apart; (b) free-running loops use the existing per-slot playhead telemetry (observeMsegPlayhead / the harness's emitEffectiveMsegState shape) to anchor phase, predicting the next boundary as now + (1 - position) * T rather than waiting to observe the wrap. MEASURE the telemetry anchor's accuracy/latency before trusting it and record the number.
    Audit findings (2026-08-19, engine + type contracts — these reshape the above):
    - MSEG rate has exactly one kind today: seconds (ui/shared/mseg.ts MsegPlayback.rate). No tempo-synced rate exists, so the BPM-visibility gate is moot until the reserved rateKind gains a sync value; drop it from v1.
    - The loop is a SUB-REGION {startX, endX} of the shape: the cycle period is T = (endX - startX) * rate.seconds, and the boundary to sync to is the region wrap (endX back to startX), NOT playhead 1 -> 0. Default playback loops the full shape with noteOffPolicy "finish_loop" and holdFinalValue true.
    - MSEGs run PER VOICE, and effectiveMsegState reports the newest audible voice (FixedFrameOscillator findNewestMonitoredVoiceIndex). Every preview strike spawns a new voice whose MSEG phase restarts at the note-on (legatoRestarts semantics to be confirmed engine-side during implementation). Consequence: the loop rhythm the user hears is anchored at a note-on JS itself observed, so the PRIMARY algorithm is note-on-anchored arithmetic for every case — engine-owned strikes AND held-chord re-strikes (a re-strike is note-off+note-on, which re-anchors). Telemetry drops to a cross-check/kill-switch input, not a phase source. Held-note bookkeeping must gain note-on timestamps to serve as anchors.
    - noteOffPolicy "finish_loop" keeps a released voice looping; its anchor remains its own observed note-on, so the arithmetic model still holds.
    Eligibility gates (attempt sync only when ALL hold):
    - The slot is in loop playback (one-shots never sync).
    - The slot has at least one enabled route (unmapped MSEGs are ignored entirely). Slot selection when several loop (user decision 2026-08-19): ALWAYS the slowest eligible loop — it is the audible rhythm, and since all per-voice MSEGs share the same note-on anchor, harmonically related faster loops land on its grid for free. The earlier edited-parameter/armed-source preferences are dropped.
    - T is confidently known and stable: skip sync while the MSEG rate itself is being edited, and skip tempo-synced rates unless host BPM is visible from JS (audit first; assumed not).
    - Telemetry anchor fresh within ~100 ms (free-running case only).
    Regime bounds (starting numbers — tune on the phone with everything else):
    - T < ~120 ms (faster than ~8 Hz): never sync. The loop reads as texture, not rhythm, and timer/telemetry jitter (±10-30 ms) is too large a fraction of T for "synced" to be true.
    - Sweet band, T between ~120 ms and the wait budget W: every due strike defers to the next cycle boundary. W by strike kind: leading strike ~150 ms (responsiveness dominates), in-motion and trailing strikes ~300 ms (rhythm dominates; the ear forgives late more than off-beat).
    - Slow loops, T > W (the musically common 0.5-3 Hz range, where the jarring is worst): implement BOTH candidate policies behind one switch so the tuning pass can compare — (a) opportunistic: sync only when the next boundary is ≤ W away, else fire immediately; (b) subdivision grid: quantize to the loop's internal binary grid T/2^k, choosing the finest interval within [~120 ms, W] (a 2 s loop gets a 250 ms grid). (b) assumes rhythmic MSEGs are drawn on binary-ish grids — verify against real patches during tuning and pick one policy explicitly.
    - Kill-switch: if two consecutive synced strikes measurably land > ~25 ms off the boundary, fall back to immediate strikes for the rest of the gesture.
    Contract amendment:
    - T12's "the final changed value must be heard no later than 250 ms after its change" becomes "≤ 250 ms + the active sync wait (≤ W)" while sync is engaged. Record the amendment beside T12's locked behavior when this lands.
    Done when:
    - The quantizer is pure with deterministic tests covering every regime, gate, and the kill-switch; a browser case drives fake playhead telemetry and proves a due strike defers to the boundary (and that ineligible cases fire immediately).
    - The telemetry anchor accuracy measurement is recorded, and tempo-sync/BPM visibility is audited and recorded.
    - Both slow-loop policies are selectable for the tuning pass; the tuning pass then picks one, tunes the bounds, and folds the ship/revise/reject into T12's closure.
